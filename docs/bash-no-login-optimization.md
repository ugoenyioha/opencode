# Technical Architecture: Bash Tool Login Shell Optimization

## 1. Analysis of Current State

### `packages/opencode/src/tool/bash.ts`

Currently, the `Bash` tool invokes `Sandbox.spawnWith` passing a command array that explicitly injects the `-lc` flags. This forces a login shell to ensure that the user's environment profiles (`.bash_profile`, `.zprofile`, `.zshrc`, etc.) are fully sourced.

```typescript
const sandboxOpts = {
  command: [shell, "-lc", params.command],
  workdir: cwd,
  // ...
  env: { ...process.env, ...shellEnv.env },
}
```

While accurate for ensuring environment parity, sourcing dotfiles repeatedly for every Bash tool invocation significantly increases latency, especially when tools like NVM or pyenv are initialized.

### `packages/opencode/src/sandbox/*.ts` (Note: `packages/opencode/src/sandbox/bash.ts` is not a physical file)

The `sandbox` module passes down the `sandboxOpts.command` directly to the `child_process.spawn` equivalents of backends like Firecracker, Linux namespaces, bwrap, gVisor, or Darwin's sandbox-exec. The latency occurs entirely in the child's bash binary evaluating dotfiles as instructed by `-lc`.

## 2. Logic to Detect a "Shell Snapshot"

To safely skip the `-l` (login) flag, we must ensure we have a valid environment snapshot (like Claude Code does).
Presently, OpenCode gathers shell environment values through a plugin hook:

```typescript
const shellEnv = await Plugin.trigger("shell.env", { cwd, sessionID: ctx.sessionID, callID: ctx.callID }, { env: {} })
```

**Proposed Check:**
We can establish a session-level caching mechanism for the "shell snapshot" where:

1. When the OpenCode process initializes or during the first tool invocation, it captures the environment generated by an interactive login shell.
2. The snapshot gets stored in memory (e.g., using `Instance.state()` or within the plugin implementation backing `shell.env`).
3. We introduce a new property `isSnapshotValid` on the returned `shellEnv` object indicating whether the returned `env` contains a completely resolved profile.

```typescript
// Proposed shellEnv payload structure
{
  env: { ... },
  isSnapshotValid: true // Indicates that the env provided is a complete snapshot from a previous `-lc` run
}
```

## 3. Modification to Skip `-i -l` When Snapshot is Valid

If `isSnapshotValid` is true, we already hold the heavy environment variables (`PATH`, aliases, custom exports) within `shellEnv.env`. We can omit the login shell flag and simply pass `-c`, yielding a drastic reduction in execution latency.

```typescript
// packages/opencode/src/tool/bash.ts

// 1. Fetch shell env and check if snapshot is valid
const shellEnv = await Plugin.trigger(
  "shell.env",
  { cwd, sessionID: ctx.sessionID, callID: ctx.callID },
  { env: {}, isSnapshotValid: false }, // Extend default payload
)

// 2. Conditionally determine shell flags
const shellFlags = shellEnv.isSnapshotValid ? "-c" : "-lc"

// 3. Apply dynamically to Sandbox Options
const sandboxOpts = {
  command: [shell, shellFlags, params.command],
  workdir: cwd,
  network: config.sandbox?.network ?? false,
  writable: [cwd, ...(config.sandbox?.writable ?? [])],
  memory: config.sandbox?.memory_mb,
  cpu: config.sandbox?.cpu_percent,
  env: {
    ...process.env,
    ...shellEnv.env,
  },
}
```

**Action Plan:**

1. Modify the internal plugin handling `shell.env` to perform a single `-lc` dummy execution (e.g., `bash -lc env` or similar), parsing the output and caching it for the lifetime of the session.
2. Update the `shell.env` trigger output to include `isSnapshotValid: boolean`.
3. Update `packages/opencode/src/tool/bash.ts` to consume `isSnapshotValid` and toggle between `-c` and `-lc`.
4. Run standard unit tests for `bash.ts` to ensure sandbox logic accepts `-c` without regression in environment capability.
