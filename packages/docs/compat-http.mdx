# HTTP Compatibility APIs

OpenCode exposes OpenAI-compatible and Anthropic-compatible APIs as core server routes.

## Enable routes

Compatibility routes are disabled by default.

Use OpenCode model IDs directly (`provider/model`), for example `opencode/gpt-5-nano`.

```json
{
  "server": {
    "compat": {
      "max_output_tokens": 32000,
      "openai": {
        "enabled": true,
        "max_output_tokens": 48000
      },
      "anthropic": {
        "enabled": true,
        "max_output_tokens": 40000
      }
    }
  }
}
```

`server.compat.max_output_tokens` sets the global cap for compatibility routes. Default is `32000`.

`server.compat.openai.max_output_tokens` and `server.compat.anthropic.max_output_tokens` override the global cap per provider.

Cap precedence per provider is:

1. Provider-specific cap (`server.compat.openai.max_output_tokens` or `server.compat.anthropic.max_output_tokens`)
2. Global compat cap (`server.compat.max_output_tokens`)
3. Built-in default (`32000`)

## OpenAI-compatible routes

- `GET /v1/models`
- `POST /v1/chat/completions`
- `POST /v1/responses`

Output token parameters:

- `POST /v1/chat/completions`: `max_tokens`
- `POST /v1/responses`: `max_output_tokens`

Auth header:

```http
Authorization: Bearer <token>
```

OpenAI-compatible routes also accept `x-api-key: <token>` as an alternative input and validate it against `OPENCODE_TOOL_ENDPOINT_API_KEY`.

If OIDC, JWT, or OAuth introspection env is configured, Bearer tokens are validated before API-key fallback.

Bearer routing:

- JWT-shaped tokens (`header.payload.signature`) use OIDC/JWT verification first.
- Opaque tokens use OAuth introspection when enabled.
- If JWT/OIDC verification fails and introspection is enabled, OpenCode falls back to introspection by default (`OPENCODE_COMPAT_BEARER_FALLBACK_TO_INTROSPECTION=true`).

OIDC verification env:

- `OPENCODE_COMPAT_OIDC_ISSUER`
- `OPENCODE_COMPAT_OIDC_AUDIENCE` (optional)
- `OPENCODE_COMPAT_OIDC_ALGS` (optional, default `RS256`)

JWT verification env:

- `OPENCODE_COMPAT_JWT_JWKS_URL` for `RS256`
- `OPENCODE_COMPAT_JWT_HS256_SECRET` for `HS256`
- Optional claim checks: `OPENCODE_COMPAT_JWT_ISSUER`, `OPENCODE_COMPAT_JWT_AUDIENCE`
- Optional clock skew override: `OPENCODE_COMPAT_JWT_CLOCK_SKEW_SECONDS` (default `30`)
- RS256 JWTs must include a `kid` that matches an RSA key in the JWKS document.

OAuth introspection env:

- `OPENCODE_COMPAT_OAUTH_INTROSPECTION_URL`
- `OPENCODE_COMPAT_OAUTH_CLIENT_ID`
- `OPENCODE_COMPAT_OAUTH_CLIENT_SECRET`
- `OPENCODE_COMPAT_OAUTH_INTROSPECTION_AUTH_METHOD` (optional: `client_secret_basic` default, `client_secret_post`, `bearer_client_credentials`)
- `OPENCODE_COMPAT_OAUTH_INTROSPECTION_TOKEN_URL` (optional for `bearer_client_credentials`; defaults from introspection URL)
- `OPENCODE_COMPAT_OAUTH_INTROSPECTION_BEARER_SCOPE` (optional for `bearer_client_credentials`, default `internal_oauth2_introspect`)
- `OPENCODE_COMPAT_OAUTH_INTROSPECTION_TIMEOUT_MS` (optional, default `5000`)
- `OPENCODE_COMPAT_OAUTH_ISSUER` (optional strict check)
- `OPENCODE_COMPAT_OAUTH_AUDIENCE` (optional strict check)
- `OPENCODE_COMPAT_OAUTH_REQUIRED_SCOPE` (optional any-of match)

Outbound auth URL policy:

- OIDC discovery/JWKS and introspection endpoints must use `https://`, or loopback `http://localhost|127.0.0.1|::1`.
- OIDC discovery `issuer` must match the configured issuer value.
- For non-loopback issuers, discovered `jwks_uri` must use the same host as the configured issuer.

When OIDC/JWT/introspection auth is enabled, invalid Bearer tokens fail closed with `401` even if `x-api-key` is also present.
Discovery/JWKS/introspection fetches use short timeouts and short failure caching to reduce repeated upstream calls during outages.

Compat auth is keyed by `OPENCODE_TOOL_ENDPOINT_API_KEY`.
Optional fallback to `OPENCODE_SERVER_PASSWORD` is disabled by default and requires `OPENCODE_COMPAT_ALLOW_SERVER_PASSWORD=true`.

Example:

```bash
curl -X POST http://localhost:4096/v1/chat/completions \
  -H 'Authorization: Bearer test-token' \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "opencode/gpt-5-nano",
    "messages": [{"role":"user","content":"hello"}]
  }'
```

## Anthropic-compatible routes

- `POST /v1/messages`
- `POST /v1/messages/count_tokens`

Output token parameter:

- `POST /v1/messages`: `max_tokens`

Required headers:

```http
x-api-key: <token>
```

`anthropic-version` is accepted for client compatibility but currently ignored by this compat implementation.

`Authorization` is ignored on Anthropic-compatible routes.

Compat auth is keyed by `OPENCODE_TOOL_ENDPOINT_API_KEY`.
Optional fallback to `OPENCODE_SERVER_PASSWORD` is disabled by default and requires `OPENCODE_COMPAT_ALLOW_SERVER_PASSWORD=true`.

Example:

```bash
curl -X POST http://localhost:4096/v1/messages \
  -H 'x-api-key: test-token' \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "opencode/gpt-5-nano",
    "max_tokens": 256,
    "messages": [{"role":"user","content":"hello"}]
  }'
```

## Streaming

- OpenAI streaming returns SSE chunks and ends with `data: [DONE]`.
- OpenAI `responses` streaming emits lifecycle events (`response.created`, `response.in_progress`, output item/content part add/done events, `response.completed`).
- Anthropic streaming returns ordered typed SSE events (`message_start` -> content events -> `message_stop`).
- Streaming and non-stream execution enforce a server timeout of `120s`.

## Request guardrails

- `Content-Type` must be `application/json`.
- Request body size is capped at `512 KB`.
- Unknown model ids return provider-compatible `404` responses.
- For internet-facing deployments, enforce a body-size limit at the reverse proxy/load balancer as well.

## Current implementation scope

- These endpoints are compatibility-focused and config-gated.
- This is a compatibility subset, not full protocol parity with every OpenAI/Anthropic field.
- Shared execution and error mapping are implemented for both providers.
- Non-stream responses map tool output into provider-shaped tool payloads (`tool_calls`/`tool_use`).
- `count_tokens` is deterministic and normalized, not model-tokenizer exact.
- Multimodal/tool block fidelity is still partial and will be expanded in follow-up work.
